# sqrtx: project notes (handoff for a new chat)

Written 2026-09-26. Read this first, then look at the code. No secrets are in this file.

## What sqrtx is
A business directory/platform. Businesses register, create a public profile (logo, address, contact info), then add products and/or services. Visitors browse. Mobile first, black and white design, Inter font.

## Accounts and services
- **Supabase** project handles login (Auth). Email confirmation is ON. The frontend talks to Supabase directly (`lib/supabase.ts`, publishable key in `.env.local`); the backend only verifies the Supabase JWT (ES256 via JWKS, also checks audience `authenticated` and the issuer). Tokens last 1 hour.
- **Trigger** in Supabase (made by hand, not in migrations): a new Supabase account creates a row in `public.users` (id, login_email). `users.id` has a foreign key to Supabase's auth users with cascade delete. Email changes are NOT synced yet.
- **Password policy** (set in Supabase AND in the form, keep in sync): 8+ characters with a-z, A-Z and 0-9.
- **Email sending**: Brevo custom SMTP with a Gmail sender (dev only). Brevo IP blocking must stay OFF (Supabase has no fixed IPs). Brevo free plan = 300 emails/day. Supabase's own limit was raised to 100/hour.
- **Domain `sqrtx.co` is NOT owned yet** (no DNS records existed when checked). So: `support@sqrtx.co` on the landing page is dead, Brevo domain authentication (SPF/DKIM) can't be done, and company URLs are shown as `sqrtx.co/<name>` using one constant (`SITE_HOST` in `lib/business-profile.ts`). Buy a domain before launch.
- **Database extras added by hand in Supabase** (not in migrations, because TypeORM can't touch the auth schema): CHECK constraints `users_onboarding_step_check` and `business_profiles_provides_check`, Row Level Security ON for all public tables, the trigger above. The backend connects as `postgres` (bypasses RLS).
- **Google Places** (address search): needs `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` in `.env.local` (empty until you add it). Enable "Places API (New)" + "Maps JavaScript API", restrict the key to your site addresses. Without it the form works but the address box says search is unavailable.
- `.env.local` variable names: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_API_URL` (http://localhost:3000), `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`.

## Registration flow (how it works)
1. **Landing** (`/`) -> Register / Log in.
2. **Register** (`/register`): email + password. Creates the Supabase account, then a "check your email" page (resend with 60s countdown, change email, auto-continue if the link is opened in another tab of the same browser, "Confirmed on another device? Continue" signs in with the password kept in memory only). An already-registered email shows "Already registered" on the form (uses Supabase's empty `identities` heuristic, not officially guaranteed).
3. **Confirmation link** brings the user to `/register/company`.
4. **Login** (`/login`): after sign-in it calls `GET /onboarding/me` (`lib/onboarding.ts`) and sends the user to the page for their step (`pathForStep`).
5. **Business profile** (`/register/company`): create mode (POST multipart) and edit mode when coming Back (PATCH JSON + PUT logo). Google address search, business category (a search box with a list: the 137 categories come from the API, `GET /business-profile/categories`, loaded together with the profile in `company-step.tsx`; the user can only pick one, never type their own; the layout of the picker is not in a design, so it is a placeholder; the list is shown under group headings (Food & drink, Shops, ...; a gray band, look is a placeholder), also while searching: results are ranked (whole-word matches first), then gathered under their group, the group with the best match first; and a line `Can't find yours? Choose "Other"` sticks to the bottom of the list, wording is a placeholder too), "Your URL" is checked for availability when the user leaves the field (green check / "already taken"), Products/Services checkboxes become `provides` (products | services | both), logo upload.
6. **Products** (`/register/products`, Figma `2225:845`, phone only): BUILT. Name, price (optional, blank shows "Inquiry"), category (the list shows at most 5 of the categories products use, most used first, from `GET /product/categories`; typing filters them and adds a last row `Create "..."`), 1-30 photos (button, or drag files onto the zone; the first is the big main photo; JPEG/PNG/WebP/HEIC). Every photo is SHRUNK IN THE BROWSER when picked (`shrinkPhoto` in `lib/photos.ts`: long side at most 2400 px, WebP quality 0.9, rotation applied, metadata gone; a photo that is already at most 2400 px and 1.5 MB, or one the browser can't read like HEIC on Chrome, goes up untouched), because phone photos are 20 MB+ and the API takes 10 MB per file (checked after shrinking). The server keeps a 2400 px WebP master as `original.webp` instead of the upload (no GPS), see API.md. The tiles draw a 600 px thumbnail (`drawThumbnail`), description (the API REQUIRES it, the design has no asterisk: the label has one, decide with the designer). "Add product" uploads it and empties the form for the next one; "Next" first adds a half-filled product so nothing typed is lost, then calls `POST /onboarding/next`; "Skip for now" does the same call and drops the form. Back goes to `/register/company`. Photos can be dragged onto another photo to reorder, swapping their places (so the first spot still decides the main photo); works with a mouse (native HTML5 drag) and with a finger (a ~350ms long-press arms it, since native HTML5 drag never fires from touch; a quick tap or a scroll doesn't). This is client-side only, before upload, and unrelated to the API's own `PUT /product-image/product/:id/order` (that one reorders an already-saved product's images, for an edit screen that doesn't exist yet). No design yet for: removing a photo (a small cross, with a 44px tap target), reordering (nor a keyboard way to do it), editing or listing products already added, the messages.
7. **Services** (`/register/services`, Figma `1909:607`, phone only): BUILT, an almost exact mirror of the products page (same fields, same behavior, same gaps) with `service_name` instead of `product_name` and its own `lib/services.ts`/`GET /service/categories`/`POST /service`. The image zone (`app/components/image-zone.tsx`) and photo-shrinking/thumbnail helpers (`lib/photos.ts`) are shared between the two forms. Reached either from business profile directly (no products step) or from the products page; Back goes to whichever of `/register/company` or `/register/products` actually precedes it for that user (checked against `onboarding/me`'s `steps`).
8. **Final** (`/register/final`, Figma `1911:712`, phone only): BUILT, the last registration step. One textarea ("About*": the design has no asterisk but the API requires it, so one was added like on the other required labels; no character limit, no placeholder), one checkbox ("I accept the terms and conditions and the privacy policy": the design only says "...the terms and conditions", the privacy part was added because the API records both versions; both parts link to /terms and /privacy in a NEW tab so the form isn't lost; the terms box works the same way: see the checkbox convention below), and Finish. Both are required; Finish focuses whichever is missing first. Calls `POST /onboarding/finish { about_company, terms_accepted: true }`, which now also stamps `users.terms_accepted_at`/`terms_version`/`privacy_version` (both versions hardcoded to `"1"` in `sqrtx/src/onboarding/onboarding.constants.ts` — bump them if the eventual real terms/privacy text changes). No Skip (it's mandatory, nothing after it). Back goes to whichever of company/products/services actually precedes "final" for that user, same pattern as services' Back. The "Finish" button is a plain black button, same style as the other pages' "Next" (a flag icon and then a checkered F1-flag background were both tried and reverted). The "30-day free trial. Upgrade only if you love it." subtext under Finish was in the design and is shown as-is even though there's no subscription/billing system anywhere in the app yet — the user confirmed this is a real planned feature, not leftover template copy.

Server-side progress: `users.onboarding_step` = furthest step reached: `business_profile` -> `products` (if provides has products) -> `services` (if it has services) -> `final` -> `done`. Only the server moves it, and it is the FURTHEST step ever reached (going back never lowers it). So "Next" on the company/products/services pages does NOT go to `state.step` (that would send someone who went back from Finish straight to Finish, skipping pages, including a step they just added by changing what the business offers): it goes to the next page on the user's own `steps` path via `pageAfter()` in `lib/onboarding.ts`. Login and the landing page's log in shortcut still use the furthest step, on purpose. Saving the profile advances it, `POST /onboarding/next {step}` advances products/services, `POST /onboarding/finish {about_company, terms_accepted}` completes registration (also stamps the terms/privacy acceptance columns, see the Final page notes below). Until `done`, the owner's profile, products and product images are hidden from every public endpoint. Public product/service reads (lists, by id, categories, images) ALSO require the owner's `provides` to include that type (`PROVIDES_PRODUCTS`/`PROVIDES_SERVICES` in `sqrtx/src/business-profile/business-profile.constants.ts`): unticking "Services" on the profile hides the services publicly but deletes nothing, and ticking it again brings them back. There is still no screen to list, edit or delete already-added items, so hidden ones can't be removed by the owner yet. Owners see their products via `GET /product/mine`. Step rules are pure functions in `sqrtx/src/onboarding/onboarding-steps.ts`.

## Conventions and preferences of the user
- Wants lean, readable code with comments that explain why. When they say "no code" answer in words only and change nothing.
- Wants claims verified (docs, measurements, tests). Say plainly what could not be verified.
- Never ask for or handle secrets in chat: they enter SMTP keys and similar themselves in dashboards.
- Do NOT create real accounts, send real emails or purchase things. Test with intercepted `fetch` responses and stand-ins (see below); the user does real end-to-end runs.
- Text for messages/labels comes from the designs; anything not in a design is a placeholder and should be flagged.
- Checkboxes are 20px with a 44 x 44 px tap area around the box (approved deviation from the 11px in Figma). Only the box and that area tick it; the words next to it do NOT (Products/Services on the profile page, and the terms checkbox on the last page, whose words hold links). The words are linked to the box with aria-labelledby.

## Gotchas
- Business categories: the one existing test profile was saved with the old placeholder value `Grocery & food`; it was moved to `grocery` by hand in Supabase (2026-09-28, confirmed by a read-only query), so every saved profile now uses a real category id.
- Inter's contextual alternates (`calt`) raise an "@" that follows a digit or capital and drop it when a lowercase letter is typed next, so an email's "@" jumped while typing. `app/globals.css` turns `calt` off for `input`/`textarea` only (headings keep Inter's normal look).
- After many edits the Next dev server can serve stale modules (errors like "Element type is invalid ... got: undefined"): restart `npm run dev` and hard refresh.
- After login, "You're logged in, but we couldn't load your registration progress" means the call to the backend failed: is the backend running on port 3000, does `NEXT_PUBLIC_API_URL` match, does the user have a `users` row?
- The Supabase default email service only sends to team members at 2 emails/hour, which is why custom SMTP (Brevo) is required.
